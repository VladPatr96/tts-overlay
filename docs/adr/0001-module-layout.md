# 0001. Модули по слоям, подключение dot-sourcing'ом

Статус: принято (2026-10-20, #3).

## Контекст

Всё приложение жило в одном `tts-overlay.ps1` на ~2200 строк: конфиг, учёт затрат, движки, воспроизведение, ввод, распознавание, интерфейс. Менять один слой, не задевая остальные, было трудно; ревью и агентам файл не помещался в голову.

## Решение

Разложить по слоям на модули `lib-*.ps1` рядом с главным скриптом:

`lib-core` (лог, конфиг, ключи) · `lib-usage` (затраты, баланс, курс) · `lib-providers` (движки, воркеры, запросы) · `lib-playback` (очередь, кэш, воспроизведение) · `lib-input` (хоткеи, выделение, буфер) · `lib-stt` (диктовка) · `lib-text` (подготовка текста, уже был).

- Подключение — dot-sourcing списком в начале `tts-overlay.ps1` через `$Root`.
- В модуле только функции. Общее состояние (`$Cfg`, `$script:*`, окно WPF) остаётся общим: функции читают его из области вызывающего скрипта.
- Запуск остаётся одним `tts-overlay.ps1`, пути относительные.
- Переносим по одному модулю за коммит, без правки логики; рефакторинг — после.

Отвергнуто:
- `.psm1`-модули — у них своя область видимости, пришлось бы протаскивать `$Cfg` и окно параметрами;
- 3 крупных файла — слои остались бы смешанными;
- файл на движок — слишком мелко, общие вспомогательные функции негде жить.

## Последствия

- Порядок подключения не важен для функций, но важен для кода верхнего уровня: модули содержат только определения.
- Функция из модуля зависит от переменных главного скрипта (`$LogPath`, `$ConfigPath`, `$Cfg`) — это явная связь, она описана в шапке модуля.
- Первый шаг — `lib-core` (#8); остальные слои — #9–#13.
